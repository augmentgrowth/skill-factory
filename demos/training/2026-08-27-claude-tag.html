Claude Tag: multiplayer Claude in Slack

Claude Tag brings Claude into the place the team is already working. The useful difference is not just convenience: the work is shared, inspectable, and correctable together.

30 min
basics, setup, live work
5 cards
one participant guide
1 review
before any broader share

The beginner rule: the channel is the boundary for shared context, access, and behavior. Restate critical context near your mention, verify what Claude can access now, and never assume a connection guarantees a specific action.

Facilitator notes
  • Open with: “Claude Code and Codex are single-player deep-work spaces. Claude Tag is multiplayer Claude: the team can see the request, inspect the work, and improve it together.”
  • Set the expectation: the first ten minutes are the mental model and access check; the rest is a practical leadership-update demo.
STEP 1

Choose the right work surface

4 min

Use Claude Tag when the work should happen with the team, not merely be pasted back afterward.

UseBest forBoundary
Tag Claude in a channelShared projects, summaries, team drafts, decisions, and corrections everyone should see.The channel’s current context and configured access.
DM or individual ClaudePrivate exploration, personal connectors, or work that is not ready for the team.Your own conversation and currently available connections.
Claude Code or CodexDeep individual work with local files or repositories, private exploration, and technical implementation.Your local project and the access you explicitly provide.
Do not overread “memory”

Claude can use nearby thread and channel context, but it is not a perfect transcript or guaranteed recall system. Put the decisive fact, date, or constraint close to @Claude and link the source when possible.

Optional quick habit — steer durable memory safely

Claude may automatically save useful notes. You can also ask it to remember a stable preference, rule, or piece of context for future work. Public-channel memories may be shared across the workspace; private-channel and DM boundaries can differ.

Never save secrets or sensitive personal, patient, customer, client, financial, or credential data. Ask Claude what it remembers, then correct or delete stale memory when that control is supported.

Copy-paste memory pattern 
@Claude, remember this for future work in this [workspace/channel]: [durable preference, rule, or context].

Do not save secrets, credentials, personal data, patient data, customer data, or client data. I have not included any sensitive values in this message. Tell me exactly what you saved and where it applies. If you cannot save or inspect memory here, say so.
Quick check

If a teammate should be able to see, correct, or reuse the work, start in the appropriate shared channel. If not, start in an individual surface.

Facilitator notes
  • Say: “The channel is the boundary” is a useful operating rule, not a promise about exact memory depth or every connector mechanic.
  • Ask for one example the room would keep individual and one they would make shared.
STEP 2

Run the access preflight

6 min · setup

Spend setup time on purpose. Verify access before asking Claude to produce the real deliverable.

Live setup — 6 min
Copy-paste access check 
@Claude, run a read-only access preflight for this supervised demo.

1. Check whether you can read each of these Slack channels now:
- [APPROVED CHANNEL 1]
- [APPROVED CHANNEL 2]
- [APPROVED CHANNEL 3]
- [APPROVED CHANNEL 4]
- [APPROVED CHANNEL 5]
- [APPROVED CHANNEL 6]
- [APPROVED CHANNEL 7]
- [APPROVED CHANNEL 8]

Return a table with one row per channel: readable, not readable, or uncertain. Do not summarize channel content yet.

2. Resolve the exact Google Drive folder named “Demo — Leadership Updates — Drafts”. Report its URL or stable ID and effective audience. Confirm there is exactly one match and that access is limited to approved internal reviewers. If there are multiple matches or broader inherited access, mark the preflight failed. Do not create the folder or document yet. Do not change permissions.

3. Confirm this originating Slack thread is an approved internal review destination with no external participants, guests, Slack Connect members, executive audience, or broader public audience. If you cannot verify that, mark the preflight failed.

4. State exactly what you verified and what remains uncertain. Do not touch Asana. Do not post, send, share, invite, or create anything. Stop after the preflight and wait for the leadership-update prompt.
Go / no-go signal

Before running, the facilitator replaces all eight placeholders with the approved private channel list. Success is eight explicit channel results plus a separate Google Drive capability result. “Uncertain” counts as not verified. If any channel is unreadable, use the fallback in Step 3 rather than accepting a silent partial update.

Known Restore state for this lesson: Google Drive is connected; Slack public channels are configured; Asana is connected. Granola access to the intended shared-notes folder is currently unverified or nonfunctional. External connections are not Slack channels, so do not add one to the channel source list.

Facilitator notes
  • If setup fails, that is a useful result. Name the gap; do not improvise around it or burn the practical half of the lesson debugging permissions.
  • Transition: “Now we know what Claude can actually see today. We can make a prompt that refuses to hide anything it cannot see.”
STEP 3

Draft the leadership update

10 min · live demo

Ask for a complete, source-linked private draft first. The executive audience does not receive anything yet.

Facilitator demo — 10 min
Main prompt — complete access
Copy-paste main prompt 
@Claude, prepare a private draft of the executive leadership weekly growth update for the rolling 7 days ending now.

SOURCES — before running, replace every placeholder below with the facilitator’s approved private channel list, then review all eight explicitly:
- [APPROVED CHANNEL 1]
- [APPROVED CHANNEL 2]
- [APPROVED CHANNEL 3]
- [APPROVED CHANNEL 4]
- [APPROVED CHANNEL 5]
- [APPROVED CHANNEL 6]
- [APPROVED CHANNEL 7]
- [APPROVED CHANNEL 8]

Use only information you can actually read. External connections are not Slack channels; do not add one to this source list. Treat learning-channel and test-channel discussion as relevant only when it materially changes a growth result, active project, risk, blocker, or decision. Exclude general learning chatter, experiments with no decision, duplicates, and stale context.

OUTPUT PRIORITY
1. Growth results
2. Project progress
3. Risks and blockers
4. Decisions needed

REQUIRED EVIDENCE AND QUALITY RULES
- Link back to supporting Slack messages or threads when possible.
- Label every statement as Fact, Inference, or Missing information.
- Never invent or estimate a metric. If leads, bookings, revenue, conversion rate, cost per lead, or another expected number is missing, write “Missing — owner/source needed.”
- Name every unreadable or uncertain channel and explain how that gap could affect the update.
- Do not silently produce an update that appears complete when access or evidence is incomplete.
- Deduplicate repeated updates across channels. Prefer the newest source and preserve meaningful disagreement.
- Keep the executive draft concise: opening snapshot, then no more than 3 bullets in each priority section, followed by Sources checked and Gaps. Aim for 700 words or fewer.
- Use scrubbed or generic wording. Do not include sensitive personal, customer, patient, credential, or confidential details.

AUTHORIZED WORKING-DRAFT FLOW
A. Confirm all eight channel results. Also confirm this originating thread is an approved internal review destination with no external participants, guests, Slack Connect members, executive audience, or broader public audience. If any channel or destination check is unreadable, uncertain, or failed, stop before synthesis and use the partial-access fallback. Do not create or post a misleadingly incomplete update.
B. If every check passes, immediately create the full update in the exact preflighted “Demo — Leadership Updates — Drafts” folder. Use the verified URL or stable ID, not a new search by name. Proceed only when its effective audience is limited to approved internal reviewers. Do not invite anyone or broaden access. Private draft creation is authorized by this prompt.
C. Immediately post only a concise summary and the document link in the verified internal originating Slack thread for Malachi’s review. Do not paste the full update into Slack. This review-thread post is authorized by this prompt.
D. Do not share with the executive team, post in an executive channel, email anyone, create or edit Asana tasks, or change permissions. Those actions require a separate explicit approval after Malachi reviews the draft.

Before creating anything, report and stop if a requested step is unsupported, any channel is unreadable, or the destination/privacy boundary is uncertain. Never substitute a different destination or broader permission.
Fallback prompt — one or more channels are unreadable
Copy-paste partial-access fallback 
@Claude, do not present an incomplete weekly update as complete.

Using the access preflight, list:
1. Readable channels and the date range actually covered.
2. Unreadable or uncertain channels.
3. Which growth results, projects, risks, or decisions may be missing because of each gap.

Then create a clearly labeled “PARTIAL DRAFT — NOT READY TO SHARE” outline using only readable sources. Include source links when possible, label facts versus inference, flag missing numbers, and do not invent metrics.

Do not create a Google Doc, post to Slack, change permissions, touch Asana, or share anything. Ask me to choose whether to fix access or explicitly authorize a partial private draft. Stop and wait.
Fictional demo metrics only

If numbers are needed to explain the format, label them “SAMPLE — FICTIONAL”: 1,240 leads; 148 bookings; $92,000 revenue; 11.9% lead-to-booking conversion; $42 cost per lead. Never let sample values appear as Restore results.

What success looks like

With complete access, Claude creates one private draft immediately and posts one concise review link in the originating thread. With incomplete access, it stops before synthesis. Nothing reaches executives and permissions do not expand.

Facilitator notes
  • The prompt was stress-tested against partial access, invented metrics, missing source links, irrelevant learning/test noise, overlong output, permission expansion, and accidental executive sharing.
  • Say: “This prompt already authorizes the private working draft and its review-thread link. Executive delivery, wider permissions, external sends, and downstream system changes still require a separate yes.”
STEP 4

Correct it together

4 min · shared correction

The demo is not finished when Claude posts a link. It is finished when the team improves the shared work.

Participant move — 2 min

Ask one participant to correct a real assumption in the Slack thread—scope, status, interpretation, or a missing owner—without introducing sensitive information. Then reply:

Copy-paste revision prompt 
@Claude, treat the participant correction immediately above as a proposed correction to this draft.

Before editing, state:
1. What assumption is changing.
2. Which section of the private draft will change.
3. Whether any other claim or metric depends on that assumption.
4. The supporting source link or named accountable owner. If neither is available, ask the facilitator to explicitly confirm the correction; otherwise keep it labeled unverified and stop.

Then revise only the private Google Doc draft. Preserve source links, fact/inference labels, missing-number flags, and the existing private permissions. Add a short revision note in this thread for Malachi’s review.

Do not share with executives, broaden permissions, create tasks, or post the full update. If the correction conflicts with a linked source, show the conflict and stop for a human decision.
The multiplayer moment

Everyone sees the correction, Claude explains its impact, and the same private draft improves. The work is inspectable instead of disappearing inside one person’s chat.

Facilitator notes
  • Choose a correction with a visible downstream effect: “This test is still exploratory, not launched” is better than a spelling change.
  • If Claude resists or over-edits, that is teachable: narrow the requested change and restate the source-of-truth boundary.
STEP 5

Reuse the habit next

6 min · wrap

Shared context, explicit evidence, a private review draft, and approval before broader action—the same shape works beyond the leadership update.

ScenarioFirst requestApproval boundary
Messy thread“Summarize decisions, owners, open questions, and next steps. Link each item to the message that supports it.”Review before posting a canonical recap.
Meeting notes → Asana“Draft proposed tasks with owner, due-date assumption, source note, and acceptance criteria.”Show proposals; create nothing until explicitly approved.
Weekly Growth Core digest“Draft a concise rolling-7-day digest from the named approved channels; expose access gaps and missing metrics.”Private/review draft before any broad post.
Prior decisions“Search only approved shared notes for the decision, date, owner, and source link. State when access is unverified.”No answer from an unverified Granola folder; use an approved readable source.

Try this next: pick one active shared thread. Ask Claude for decisions, owners, open questions, next steps, and source links. Correct one assumption together before treating the recap as final.

Optional bonus — individual connectors, Asana, Granola, and future routines
  • Individual connectors: connector support reported around Aug 21 may broaden what an individual Claude surface can do. Treat it as an experiment until official documentation and live access are verified; do not promise parity with channel access.
  • Asana: Restore has a connection, but begin with proposed tasks. Require explicit approval before creation or edits.
  • Granola: access to the intended shared-notes folder is currently unverified or nonfunctional. Never teach “search all meeting notes” as guaranteed until a live preflight passes.
  • Ambient behavior and routines: keep proactive posting off initially. Pilot a narrow, predictable routine only after the manual workflow is trusted, the destination is explicit, and review/stop rules are proven.
