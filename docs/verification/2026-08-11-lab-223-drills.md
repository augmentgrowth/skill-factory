## 1. History secrets sweep

**Ran:** `tests/secrets-sweep.sh` → CLEAN, 166 blob/path pairs across 49 commits.

The tree was never the interesting part. The gate's `range` check already walks
every outgoing commit, so a committed-then-deleted secret cannot ship from the
moment the gate existed; what had never been examined was everything that
predated it. The sweep reads every blob in every commit's tree.

**It found something on its first run.** A synthetic AWS key — `AKIA` followed
by the alphabet in order — in a credential-scrubbing test under the old
`fable-codex` skill, present only in history since that skill moved out of this
repo. Obviously never a real credential. Allowlisted by path with that reasoning
recorded in the script.

(The first draft of this file spelled that value out, which made the sweep flag
*this document* on the next run. Correct behavior, and a useful reminder: do not
write key-shaped strings into records, even synthetic ones. The literal is gone
from the current text, but the original blob is still in history at `7e04776` —
which is precisely what a history sweep is for — so this path is allowlisted
too. That allowlist entry is scoped to this dated, closed record.)

That finding is the argument for the sweep existing. A sweep that had returned
clean on the first run would have told us nothing about whether it works.

**Controls — now automated.** A secret added then deleted is still found; a
`.env` committed at any depth is found; a clean repo with a tracked
`.env.example` passes. These lived only in this document until review pointed
out the obvious: the sweep spends no model session, so nothing justified keeping
it out of the suite. They are now `SecretsSweep` in `tests/test_release_gate.py`,
along with the three evasions found in review.

**What review found, and it was serious.** The first version required the
assignment's value to be **quoted**, and matched case-sensitively. Real
credentials are neither:

```
AWS_SECRET_ACCESS_KEY=wJalr...      unquoted, uppercase — every .env file
password: hunter2...                unquoted YAML
export DB_PASSWORD=s3cret...        unquoted shell
```

All three passed CLEAN on a repo that genuinely contained them. The sweep caught
prefixed provider keys (`sk-ant-`, `ghp_`, `AKIA` IDs) and essentially nothing
else, while its own header called it "deliberately noisy." Quotes are optional
now, matching is case-insensitive, and JWT / `Authorization:` / `sk-proj-`
shapes were added. All five shapes are pinned by tests.

Bare high-entropy hex runs are still **not** scanned for, deliberately: a
40-char hex run is also every git SHA, and this repo's docs are full of them.
That boundary is recorded in the script so it stays a decision rather than an
oversight.

## 2. Credential drill

**Ran:** `tests/credential-drill.sh` → PASS, both halves.

Mechanical (pure git facts):

- `.env` ignored at repo root **and** inside `.claude/skills/<name>/` — the
  "recursively" in LAB-223's wording, now actually tested
- `.env.example` is trackable
- a repo-wide `git add -A` stages no `.env`
- no `.env` reached history
- the sweep is still clean after the drill's own commits

Behavioral (one real headless session, handed a synthetic key the way a builder
would paste one):

- the key **value** never appeared in the session output
- nothing the session wrote is stageable as a `.env`
- the session left the key in **no tracked file** (added after review)
- the history sweep is clean **after** the session's commits (added after review)

**The false pass review found here was the worst one.** The original behavioral
half checked three places: `*.example` files, a dirty `.env`, and the transcript.
A session that wrote the key into `config.json` and committed it passed all
three — reproduced. A credential drill that green-lights a committed credential
is worse than no drill, because it converts an unknown into a false assurance.
The drill now greps every tracked file for the key and re-runs the sweep *after*
the session, so the actor most likely to mishandle the key is no longer the one
actor never audited.

The `--control` arm was itself too narrow: it only broke `.gitignore`, so it
could never have exposed this. It now plants the key in a tracked file as well,
giving two independent failure classes.

The claim under test is deliberately narrow. The variable *name* legitimately
appears — writing `ANTHROPIC_API_KEY` into `.env.example` is correct behavior.
The spec's no-key-names rule governs error messages, not setup.

**Control:** `--control` strips `.env` from `.gitignore` and requires the drill
to fail. It does, on 5 checks. That arm paid for itself immediately — it exposed
a hole in the sweep, where `rev-list --objects` attributes a blob to exactly one
path, so the same key committed to two paths reported once. Identical content at
an allowlisted path would have masked a forbidden one. Fixed.

## 3. README fallback wording

**Ran:** `tests/coldread-audit.sh HEAD 57e19e5` → the post arm answers Q5
correctly; the control arm demonstrates the defect.

This criterion had regressed. The push policy rewrote `README.md:35`, so
whatever was true before was unverified. The cold read settled it without anyone
grading their own homework:

> **Control arm** (`57e19e5`, README before the fix): "the remote must be yours
> and writable ... **that's the only stated condition**, and README describes no
> one-time setup step on your part beyond the clone itself."

That is exactly the defect: write access was necessary but not sufficient, the
release gate was also necessary, and the gate only runs from a hook that git
will not let a repository install for itself. A reader following that wording
would believe their pushes were gated when nothing was checking anything.

> **Post arm:** names all three — remote ownership, the gate failing closed, and
> the one-time `git config core.hooksPath githooks`, including *why* the manual
> step exists and when you can skip it.

Q2 (auto-commit crons unacceptable) and Q3 (never rewrite history) held in both
arms, as required.

**Note on Q1a.** The audit's written criterion says Q1a must flip. It did not
here, and that is correct: the control ref `57e19e5` already contains the push
policy, so this run isolates the README change and **Q5 is the discriminating
question**. The script's guidance now says so, because a future reader would
otherwise have read an unmoved Q1a as a failed audit.

## 4. Ten-minute instantiation

**Ran:** `tests/instantiation-drill.sh` → **8m49s** against a 600s target, with
`weekly-support-digest` committed (4 files tracked) and `cases/baseline/`
present. PASS.

**The caveat is not decoration.** This times the *agent's* path — clone plus one
frozen prompt. A real builder also reads, thinks, and types. Treat 8m49s as a
**floor** under the README's "under 10 minutes" claim, not as confirmation of
it. At 88% of the target with no human in the loop, the human-inclusive claim is
closer to the edge than the README's tone suggests. Worth revisiting the wording
if the number moves.

**Two runs failed before this one, both in the harness rather than the factory,
and both are worth knowing about:**

1. **A fresh clone is not a fresh session.** The first run inherited the
   operator's personal `~/.claude` tier, found an already-built skill for this
   exact workflow among their personal skills, correctly declined to build a
   duplicate, and reported 58 seconds. A drill that measures one machine's
   installed skills is worse than no drill: it produces a fast, passing-looking
   number. `--setting-sources project,local` drops the personal tier while
   keeping the project `CLAUDE.md` that *is* the factory. The same leak applied
   to the cold-read audit — where personal instructions contaminating a "cold"
   read defeats the entire point — and to the credential drill's session. Both
   were fixed before the runs recorded above.
2. **Dropping the user tier drops the permission allowlist.** The second run
   built the skill correctly and then had nowhere to write it.
   `--permission-mode bypassPermissions` stands in for the human who clicks yes.

**Incidental evidence for the hook fix.** In run 2, the session's preflight
noticed the throwaway clone's gate was not installed and said so unprompted:
*"this clone's push protection isn't switched on, and I couldn't switch it on
either."* It could not set it only because that run had no permission to run
`git config`. The preflight change in `9135d07` is doing what it claims.

## 5. The hook-install fix was itself unsafe (found in review)

Not a drill, but it belongs in this record because it is the most serious thing
the review pass found and it shipped in 0.3.3.

`9135d07` told the agent: *"if the build home has a `githooks/pre-push`, ensure
`core.hooksPath` is `githooks`."* Setting `core.hooksPath` arms **every** hook in
that directory, not just the gate. Under a plugin install the build home is
whatever repo the builder happens to be standing in, so a hostile repo carrying
a `githooks/pre-commit` would have it executed on the factory's first commit.
Git's refusal to honor cloned hooks is exactly the protection that instruction
gave away, keyed on a filename.

Two more defects in the same three lines: the instruction never said the config
write must be **repo-local**, so a cold agent could plausibly run it `--global`
and silently disable hooks in every repo on the machine; and it had no branch for
a repo whose `core.hooksPath` already belongs to husky or pre-commit, which it
would clobber without a word — while an adjacent bullet in the spec already
establishes escalation as the pattern for exactly that collision.

The instruction now requires all three: the hook must verifiably invoke
`scripts/release-gate.py`, the config write is repo-local and never `--global`,
and an existing foreign value escalates instead of being overwritten.

Separately, the fix had been applied to only **two of the four** skills that
push. `graduate-skill` and `learn-from-session` commit and push under the same
contract, so a clone whose first factory operation was either of those still
pushed unguarded — the exact hole the change existed to close. All four carry the
preflight now.

## What the review pass changed about how this is verified

The three drills were written to be repeatable, and two of them still could not
fail in the ways that mattered. The pattern in all three defects was the same:
**the check looked where the problem wasn't.** The sweep matched shapes real
credentials don't take, the credential drill audited every actor except the
session, the instantiation drill read the index instead of the commit.

What changed structurally, beyond the individual fixes:

- `secrets-sweep.sh` and `credential-drill.sh --mechanical-only` cost no model
  session, so their controls are pytest cases now (`SecretsSweep`), not prose in
  this file. 44 tests and 5 subtests.
- Every shell drill gets a `bash -n` parse check in the suite. They were
  excluded from pytest for spending model sessions, which left them with no
  guard at all — a typo would have surfaced weeks later, by hand.
- The sweep fails closed. It had no `pipefail`, so a git failure mid-scan
  produced a short blob list and still printed CLEAN: a broken scan and a clean
  repo were indistinguishable. In a repo whose entire release story is "the gate
  fails closed," that was the wrong default.
